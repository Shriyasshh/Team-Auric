# Phase 3 QR Redesign - Technical & Database Specification

This document summarizes the changes applied to the database and backend logic for transitioning the old Phase 2 "Search & Request" workflow into the new Phase 3 "QR Scan & Upload" care-session architecture.

## 1. Objects Dropped
The following obsolete tables, functions, and policies were completely removed:
- `DROP FUNCTION IF EXISTS public.search_doctors(TEXT);`
- `DROP FUNCTION IF EXISTS public.search_patients(TEXT);`
- `DROP TABLE IF EXISTS public.access_requests;`
- `DROP TABLE IF EXISTS public.access_permissions;`
- All existing visibility policies on the `profiles` table.
- All existing visibility policies on the `medical_records` table.

## 2. Objects Created & Altered

### `qr_sessions` Table (Created)
Stores the short-lived tokens generated by patients.
- `token_id UUID PRIMARY KEY DEFAULT gen_random_uuid()`
- `patient_id UUID NOT NULL REFERENCES public.profiles(id)`
- `created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`
- `expires_at TIMESTAMPTZ NOT NULL DEFAULT NOW() + INTERVAL '5 minutes'`
- `status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending', 'claimed'))`
- `claimed_by_doctor_id UUID REFERENCES public.profiles(id)`
- `claimed_at TIMESTAMPTZ`

### `medical_records` Table (Altered)
- Added `created_by_doctor_id UUID REFERENCES public.profiles(id) ON DELETE SET NULL`: Identifies the authenticated doctor who created the record. It is `NULL` for legacy patient-created records.
- Added `blockchain_status TEXT NOT NULL DEFAULT 'PENDING' CHECK (blockchain_status IN ('PENDING', 'ANCHORED', 'FAILED'))`: Tracks the status of the MST Integrity Proof transaction.

## 3. RLS Policy Summary

### `qr_sessions` Policies:
- **Patients** can `SELECT` their own QR sessions (`patient_id = auth.uid()`).
- **Doctors** can `SELECT` QR sessions they claimed (`claimed_by_doctor_id = auth.uid()`).

### `medical_records` Policies:
- **Patients** can `SELECT` their own records (`patient_id = auth.uid()`).
- **Doctors** can `SELECT` records they created (`created_by_doctor_id = auth.uid()`).
- **Doctors** can `INSERT` records *only* if they set `created_by_doctor_id = auth.uid()` AND they currently hold an active, unexpired 2-hour QR care session for the target patient.

## 4. Backend / FastAPI Authorization
FastAPI must actively verify the authorization boundaries. Before uploading a file or inserting database records, FastAPI extracts the authenticated Supabase JWT and executes a service-role validation query (or `claim_qr_session`) to ensure:
- The user is authenticated with `role = DOCTOR`.
- The target patient is linked to an active `qr_sessions` row where `claimed_by_doctor_id = auth.uid()`.
- The `status` is `claimed` and `claimed_at` is within the last 2 hours.

## 5. Migration Risk & Unresolved Issues
- **Migration Risk:** The old Phase 2 architecture relied on patients uploading their own files, so `created_by_doctor_id` is set to `NULL` for existing records to prevent data loss. The UI must safely render these legacy records by defaulting to "Uploaded by Patient" if the doctor ID is missing.
- **Unresolved Issue:** There is currently no UI implemented to generate the QR code, scan it, or create a record for a patient. The FastAPI file upload endpoint also needs to be updated to inject and validate the `created_by_doctor_id` against the active QR session.
