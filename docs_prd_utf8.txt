1. Executive Summary
MediVault is a privacy-first medical record management platform intended for patients and doctors. The product concept is to give patients a unified place to manage medical records, while allowing them to control access to those records and verify their integrity. The core system keeps sensitive medical files off-chain and encrypted, while MST Blockchain is used as a trust and audit layer for record integrity proofs and access events.
The supplied project specification defines the central separation as: off-chain storage for privacy, blockchain for integrity and auditability, and application logic in the web/API layer. The organizer track guide further requires meaningful MST use, MST Testnet deployment, a public GitHub repository, and at least one verifiable MST Testnet transaction. fileciteturn1file0L10-L25
Core product principle
MediVault must not be “a normal medical-record app plus a wallet.” MST Blockchain must participate in core product behavior: record integrity proof and/or consent/access audit events must be real on-chain operations.

PART II — SOFTWARE REQUIREMENTS SPECIFICATION (SRS)
11. System Architecture
The technical architecture replaces the earlier Django-centered design with the user-approved modern stack: Next.js/React for the application UI, Supabase for managed Auth/PostgreSQL/Storage/RLS, FastAPI for security-sensitive server-side processing where required, and MST Blockchain for the on-chain trust layer.
Architecture boundary
The system is intentionally split into four concerns: presentation, managed application data, secure processing, and blockchain trust/audit. This reduces unnecessary duplication while keeping security-sensitive operations server-side.

16. Encryption and Integrity Specification
16.1 Encryption
The intended MVP uses authenticated encryption such as AES-GCM. The exact key lifecycle is still a design decision that must be finalized before implementation: how the encryption key is generated, where it is stored, how it is associated with the patient, and how authorized doctors receive decryption capability without exposing a master key.
Medical file   ↓AES-GCM encryption   ↓Encrypted object   ↓Private Supabase Storage
16.2 Hashing
The current proposal is to hash the encrypted file using SHA-256, because that makes the integrity check tied to the exact stored encrypted object. This remains DEC-02 until confirmed.
Encrypted file   ↓SHA-256   ↓recordHash   ↓MST smart contract
16.3 Verification semantics
A successful comparison means the file presented for verification matches the hash registered on-chain. It does not prove the truthfulness, medical correctness or clinical interpretation of the document.

31. Judge Q&A Reference
Question
Answer
Why blockchain?
MediVault uses MST as a trust/audit layer for integrity proofs and consent/access events. The medical content remains encrypted off-chain.
Why not just use PostgreSQL?
PostgreSQL is still used for application data. MST adds an independently verifiable on-chain proof/event layer for the specific trust requirements.
Why not store files on-chain?
Medical files are sensitive and potentially large. Keeping them off-chain avoids exposing sensitive content and avoids turning the blockchain into a file store.
What does hash verification prove?
It proves that the compared object matches the hash registered on-chain. It does not prove medical truth or diagnosis accuracy.
Why Supabase?
It provides managed Auth, Postgres, Storage and RLS in one platform, reducing infrastructure complexity for a hackathon MVP.
Why FastAPI?
Only for server-side secure processing such as encryption, hashing, validation and selected blockchain services; it is not intended to duplicate Supabase CRUD.
Why BridgeKey?
It is the official wallet recommended by the organizer for MST wallet connection, network switching and contract signing.
What is on-chain?
Only minimal proof/state such as record identifiers/hashes, wallet references where needed, timestamps and access events.
Is MediVault production-ready?
No. It is a hackathon MVP. Production use would require additional security, key management, regulatory, interoperability and operational controls.

34. Scalability Plan
The MVP architecture is designed so each major layer can evolve independently. Supabase/PostgreSQL can scale database resources; storage can move to a higher-capacity object-storage configuration; FastAPI can be replicated behind a load balancer; Next.js can remain independently deployed; and MST transaction volume can be handled by a dedicated blockchain service/queue when the product grows.

35. Limitations
The hackathon MVP is not a production healthcare system.
Free-tier hosting is quota- and availability-limited.
Document encryption key management is a critical area requiring final design before production.
The blockchain proof only covers what is actually hashed and recorded.
The system does not establish the medical correctness of a document.
Healthcare interoperability is outside the initial MVP unless explicitly added.
BridgeKey/MST SDK capabilities must be validated against current official documentation at implementation time.
